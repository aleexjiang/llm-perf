# 评测体系架构：指标、分层与减法纪律

> 2026-09-12 架构讨论定稿。回答三个问题：工具往哪长（四层模型与三类测试）、什么不该再长（指标冻结与减法纪律）、

> 状态标记：【已拍板】= 讨论结论；【待拍板】= 有推荐方案等确认；【条件触发】= 明确不做，复活条件写明。

## 0. 一页纸结论

1. **指标只有四个数**：TTFT、decode 速度、goodput@SLO、正确性 canary。其余一切是归因诊断或工作点控制。指标层冻结。
2. **四层模型**：测试类别（suite）× 流量模型（driver）× 负载定义（workload）× 保真底座。suite 层今天不存在——"功能很多但没有章法"的根源就是它。
3. **三类测试**：基准（可比的标准化格子）、性能（容量与瓶颈归属）、稳定性（时间轴）。现有功能按"回答什么问题"归位后，缺的只有 suite 语义、时长制原语和稳定性报告面。
4. **trace 与 filler 分工**：trace 是负载层第一公民，第一交付物是离线画像（翻译器）；filler 是受控变量仪器，不因 trace 降级。多模型混合回放降级为条件触发。
5. **减法三条**：指标层冻结；配置面不开新顶层旋钮；报告做一页纸收敛。

## 1. 指标第一性原理【已拍板】

LLM 服务的体验可以完全分解，没有任何用户体验逃出这个式子：

```
E2E = 排队等待 + prefill(全部输入) + N输出 × decode(逐token)
```

- **prefill**：算力问题，一次算完所有输入 → 决定 TTFT；
- **decode**：显存带宽问题，逐 token 串行生成 → 决定出字速度；
- **排队**：容量问题，需求超过槽位/算力时发生 → 决定高负载下的一切。

| 指标 | 回答的问题 | 物理决定因素 | 判据出处 |
|---|---|---|---|
| TTFT | 等多久开始出字 | prefill 速度 + 排队 | [latency-baselines](latency-baselines.md) 三档制 |
| decode 速度（TPOT / 聚合 tok/s） | 出字顺不顺、快不快 | 显存带宽 × 并发 | 阅读速度 4 tok/s 锚点（latency-baselines §8）；ITL 平稳度（p99−p50）并入本指标的方差口径，不单列 |
| goodput @ SLO | 体验达标前提下能接多少活 | 前两者 × 槽位/调度 | 达标率默认 ≥95%（与速率扫描"goodput 达标上限"口径一致），`slo:` 段可覆盖；真机标定后调 |
| 正确性 canary | 我们测的数是不是真的 | — | 工具自指的必需品 |

**冻结宣言**：`TurnMetrics` 核心字段封版；新增字段必须指认四个数之一，否则 `json:"-"` 只进诊断面。缓存命中率、排队深度、服务端指标、stall trace……都不是指标——是这四个数变坏时的归因诊断，或是把系统放到某个工作点的控制手段。

## 2. 四层模型【已拍板】

```
┌ 测试类别 suite ── 基准 | 性能 | 稳定性 —— 决定跑哪些格子、报告模板、判定与退出码语义
├ 流量模型 driver ── 顺序 / 闭环爬坡 / 开环 Poisson / 时长制 soak
├ 负载定义 workload ── filler（受控合成） | trace 回放（真实会话）
└ 保真底座 ── client 计时 / probe 标定 / smetrics / 守卫（stall + saturation + canary）
```

现状映射：workload 层已横向贯通（`dataset.mode: filler|trace` 三场景共用）；driver 层有顺序/闭环/开环（缺时长制）；底座齐（saturation_guard 已落地，2026-09-12）；**suite 层不存在**——每次测试手工按 scenario-guide 拼格子，"章法"只活在文档里没进工具。

注意：suite 是编排语义，不是新测量机制。"受控变量优先"的定位（AGENTS.md）不变——分层是把章法显式化，不是改变测量哲学。

## 3. 三类测试【已拍板】

| | 基准 | 性能 | 稳定性 |
|---|---|---|---|
| 回答的问题 | 这台部署什么水平（跨部署/跨时间可比） | 能撑多少、瓶颈在哪 | 跑得久吗、会不会越来越慢/挂 |
| 负载 | 固定标准化格子（filler 阶梯） | 客户流量形状对齐的负载 | 持续滚动的会话 |
| 流量 | 小并发、fixed_seed、多 run | 闭环爬坡→开环扫率→mix | 时长制 soak |
| 输出 | SLO 徽章基线 | 容量曲线、饱和点、goodput@SLO、瓶颈归属 | 退化曲线、正确性时间线、事故留痕 |
| 退出码 | 有 | 无（探索性） | 有（不达标即红） |

现有能力归位：**基准** = probe 标定 + filler 阶梯 + fixed_seed + plan 画像 + SLO 三档（齐）；**性能** = 爬坡/开环/mix/goodput/速率容量曲线 + saturation_guard（齐，2026-09-12 GuideLLM 对照落地，见 ROADMAP 第 9 节）；**稳定性** = 守卫全在（stall_guard、saturation、canary、恢复探针），**缺负载原语（时长制+续跑）与报告面**。

【已拍板】suite 形态 = 配置顶层 `test: benchmark|performance|soak` + 单二进制不动（改动面小、smoke 兜得住）；子命令入口方案否决（CLI 改动面大）。suite 落地前以"预设配置 + 报告标注模式"过渡。

## 4. trace 与 filler 的分工【已拍板】

关系一句话：**trace 是翻译器，把客户流量翻译成测试参数；filler 是受控变量仪器，执行测量。** filler 的工作不是"像真实流量"，是"每个变量干净、每个口径诚实"。

### filler 已做对的（地基，不动）

- **会话内真实闭环**：multiturn 逐轮把服务端实时生成的真实回复截断后塞回 history（`KeepAssistant`），每轮新增量按服务端实测 prompt 差值动态校准——带 usage 反馈环，比假 reply 保真；
- **缓存对照三件套**：`fixed_seed` 档内复用测缓存热身 / `seed_salt` 换盐隔离冷路径 / 预热用唯一时间戳内容不污染被测前缀；
- **口径卫生**：实际 token 以 usage 为准；`NewTokens` 钳 0 防负增量污染 prefill 斜率；失败轮不推进基准防"整条 history 算新增"。

### filler 两个决策点

1. 【已拍板，默认 true】**`multiturn.shared_base`（跨会话基座共享）**：现状 `sessionSeed` 进 `SystemMsg` → 每会话 35K 基座内容互不相同（模拟"每用户个性化基座"）；另一主流形态是"一套部署一套提示词 + 工具定义"跨会话共享基座，multiturn 首轮 TTFT 差一个数量级（暖前缀 2s vs 冷 67s @200K）。做成开关两个形态都测（它本身就是新的受控变量，回答"跨用户共享前缀优化值多少 TTFT"）。AgentLens 取证首调命中仅 0–16%，说明真实共享率存疑（n=4 不足以下断言）——恰好证明两种形态都值得测。**默认 true**（"一套部署一套提示词"是私有化 agent 的主流形态）。
2. 【已拍板】**token 口径**：构造是估算式（`CharsPerToken` zh 1.4 / en 4.0 全局常数；zh 合成路径 1 字=1 token 与语料路径 1.4 还互相打架），无 tokenizer 反馈 → 跨模型"同档"实际不是同档（结论不错但格子漂移、横轴不齐）。拍板组合：**probe 自举校准**（发已知构造样本、usage 反推 chars/token 回填系数——复用 decode_speed 的"probe 实测标定"模式，零新依赖）+ **报告横轴一律 usage 实测分箱**（纯 Python 兜底）。不引入真实 tokenizer 库（依赖重，且"测试工具绑定被测模型 tokenizer"有循环性）。

### 明确缓做【条件触发】

内容形状保真（结构化语料 / 真实 `tools` 字段模拟）。影响分析：prefill 计算量 ∝ token 数，内容类型对速度本身是二阶影响；受影响的只有 chat template 对 tools 段的渲染布局与缓存边界形状。**复活条件：filler 与 trace 回放的 prefill 速率系统性偏差 >10% 且归因到内容形状。**

### 好消息

稳定性测试（时长制 soak + 会话续跑）在 filler 下**无依赖障碍**——内容生成器确定性在，会话滚完换新 seed 重开即可。soak 不阻塞在 trace 上。

## 5. 多模型（单端点）策略【已拍板】

形态：一个网关按 `model` 字段路由到 N 个模型，各模型独占 GPU 实例（不混用——2026-09-12 确认，这是后续所有判断的前提）。

**三分归因框架**（续"产品慢 vs 服务慢"的诉求，细到模型粒度）：

| 问题 | 怎么测 | 判据 |
|---|---|---|
| ① 哪个模型慢 | 逐模型隔离测试（现有 model × scenario 循环，零改动） | 各模型 vs 各自基线徽章 |
| ② 链路慢（各模型都达标但整体慢） | 调用链分解：一个用户轮串了哪几个模型、各段耗时占比 | trace 画像 + 隔离数据组合预测 |
| ③ 混合才慢（单独快、混起来慢） | 【条件触发】混合回放 vs 隔离对照 | 共享资源竞争量化（网关/宿主机/同引擎 LoRA） |

**默认路径 = 隔离优先 + 组合预测**。依据就是 scenario-guide §0 的总原则：GPU 独占 ⇒ 交互效应弱 ⇒ 叠加预测成立 ⇒ 混合回放的边际信息接近零，不该预支测它。混合回放降级为诊断器，**复活条件：组合预测与客户线上体感失配，且已排除客户端/网络因素**（届时才做 trace per-call model 字段 + 路由 driver + per-model guard 聚合）。

多模型下必须的小修（与混合回放无关，现在逐模型跑同一份配置就已踩口径）：probe `decode_speed` 建议值按单模型实测，全局 `min_tps` 套用到更慢的模型会误杀 → per-model `stall_guard` 覆盖，或规则定为"按最慢被测模型标定"。

trace 画像器（离线、不发包：per-model 流量画像 + 每轮调用链序列）是 ② 的数据源，但 **trace 线整体暂缓**（2026-09-12 拍板"后边再说"），见 ROADMAP 10.7。第一版范围限定：只做"每轮模型调用序列"，不做历史耗时参考线（历史值混着当时负载，容易从参考线被误读成判定线）。

## 6. 客户端计时立场【已拍板】

客户端计时是**测量点选择，不是缺陷**：归因"产品慢 vs 服务慢"必须在客户端测——真实用户也是客户端，网络路径包含在内是特性不是误差；换服务端埋点反而丢掉排队+网络的体验真值。

风险定量：每 chunk 处理 µs 级（读 socket + 小 JSON 解析 + 时间戳）vs 被测间隔 18ms+（真机 ITL p50）——**3~4 个数量级余量**；并发 32 流 ≈ 350 chunk/s，单核负载 <1%。危险形态只有一种：数百并发流 + 高 chunk 率 → 客户端自己成瓶颈、ITL 虚高——离当前客户场景的并发档位很远。已有防线：DisableCompression（压缩攒批破坏 ITL）、连接池 256/128。

**缺的一条守卫**：两源一致性检查——客户端实测聚合吞吐 vs smetrics 服务端生成吞吐，偏差超阈值（建议 15%）报告标注"客户端可能有损"；观测缺失按证据分级记 NA 不判失败。它不证明工具没问题，它**在被污染时说出来**。

## 7. 减法纪律【已拍板】

"加法"的逐层诊断：指标层几乎没加（`TurnMetrics` 长期稳定，健康）；诊断层加得多但都是测量有效性必需——熔断防白跑、canary 防测垃圾（自指复杂度，不是 sprawl）；控制层每个背后有真机教训背书；**真正失控的是配置面与报告面**（旋钮和页面多了）——用户感知"复杂"主要来自这里。

三条纪律：

1. **指标层冻结**（见 §1）；
2. **配置面不开新顶层旋钮**：新能力优先做成预设配置/文档指南（像 scenario-guide 给跑法、不给开关）；必须配置化的进 `model_overrides` 式差异段，不进全局面；
3. **报告做减法**：一页纸重构——顶层 = 四个数 + 徽章 + 归因结论，现有各区降级附录。同时服务"非专业友好"（客户看第一页就够）与专业排障（附录全量保留）。

**加法准入门槛**：新功能立项前回答两个问题——"你服务于四个数中的哪个？你属于控制层还是诊断层？"指认不出不做；条件触发项一律写明复活条件（清单见 ROADMAP 第 10.6 节）。

## 8. 拍板记录（2026-09-12，按推荐方案定案）

1. **suite 形态 = 配置顶层 `test:` 字段**；子命令方案否决（见 §3）；
2. **`multiturn.shared_base` 默认 true**（基座跨会话共享为默认形态，见 §4）；
3. **goodput@SLO 达标率默认 ≥95%**（与速率扫描"goodput 达标上限"口径一致，`slo:` 段可覆盖）；soak 漂移判定线默认 15%（末时段 goodput 比首时段掉 >15% 判退化 ❌）——两者真机标定后调；
4. **trace-real-16 暂缓转正**：基准套件默认全 filler 格子，跨部署可比由 filler 标准格承担；随 trace 线（ROADMAP 10.7）重启再议；
5. **token 口径 = probe 自举校准 + 报告 usage 实测分箱**（见 §4）。
