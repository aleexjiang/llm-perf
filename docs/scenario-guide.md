# 场景选型指南：测什么、不测什么、为什么

> 面向使用者：真机窗口有限，本文决定一轮测试该铺哪些格子、该砍哪些格子，以及砍的依据。
> 使用方法见 [README](../README.md)；结果 JSON 口径见 [data-contract.md](data-contract.md)；
> 延迟基线见 [latency-baselines.md](latency-baselines.md)。
>
> 依据：2026-09-12 PRO5000 真机轮（2×RTX PRO 5000 72GB TP=2，Qwen3.8-27B，vLLM v0.27.1，
> 8 格矩阵跑完 4.5 格后因服务事故终止）的实测教训。数据归档在测试工作空间 `llm-perf-test/README.md` §8。

## 0. 一条总原则

**一个格子的价值 = 它能回答的独占问题数，不是它覆盖的组合数。**

- 跑之前先问：这个格子的结果能否由已测格子**叠加预测**？能 → 不测。
- 叠加预测成立的依据是**交互效应弱**。每轮先用便宜格子验证交互弱不弱：
  TPOT 随并发/深度的变化幅度、TTFT 形态是否独立成立。交互强时才值得铺全矩阵。
- 真机窗口是稀缺资源，且稳定性事故随时打断一切——**预检和稳定性排查的优先级高于任何组合格**。

## 1. 必测清单（按执行顺序）

> 本节清单已编成预设配置 **`configs/benchmark.yaml`**（`test: benchmark`）：
> `bench -c configs/benchmark.yaml --turns both --concurrency 1,2,4,8` 一条命令覆盖场景 1–3，
> 场景 4 由 `thinking.mode: both` 自动展开，场景 5（条件格）见该文件头部命令。
> 预设固定了**格子、filler 口径、判据来源**——跨部署横比的前提正是这三者一致，
> 所以不要为"跑得更全"去改预设里的档位（要铺更多格子请另开 performance 类别的配置）。
> 报告侧按 `test` 类别切换结论区：benchmark 先说标准格水平，不追容量拐点。

### 0. 预检与标定（不是场景，但永远第一步）

`/v1/models` 连通性 → 单流流式请求标定真实 TTFT/ITL/decode 速率 → 据此复核 `stall_guard.min_tps`
（空闲窗口均值不能当稳态，实测差 5×）→ `nvidia-smi topo -m` 与卡占用 → 容器日志关键字
（实际 KV 容量、MTP 是否生效、CUDA graph 是否 capture）。
**为什么**：min_tps 定错会熔断毁掉整轮；标定数字决定后续所有格子的耗时预算；KV 容量决定并发档位怎么设。

### 1. single·off 上下文阶梯

`--turns single --concurrency 1 --thinking off`（fixed_seed，runs≥3）

回答四个独占问题：TTFT–深度曲线（prefill 速率及其衰减）；**TPOT 是否随深度不变**
（决定长上下文业务的容量模型）；prefix cache 冷热差（run1 vs run2/3）；单流 decode 基线。
实测锚点：冷 TTFT 0.9→67s（4k→200k），热跑 0.44→1.85s（20k 档 7×）；TPOT p50=18.2ms 在 4k 与 200k 同速。

### 2. concurrent·off 闭环爬坡

`--turns single --concurrency 2,4,8 --thinking off`（level 1 由场景 1 承担，别写进列表重跑）

回答：并发扩展曲线；**瓶颈归属判别**——TPOT 几乎不随并发变 ⇒ 瓶颈在槽位/排队（调服务端参数），
TPOT 随并发线性涨 ⇒ 算力到顶（加卡/副本才有效，PCIe 互联下 TP 扩展要慎重）。
实测锚点：`max_num_seqs` 4→8 使 level8 聚合 165→249 tok/s、TTFT p50 26.1→2.5s，而 TPOT 仅 21→23ms
——典型的槽位瓶颈，一次参数调整拿到 +51%。

### 3. multiturn·off 多轮会话

`--turns multi --concurrency 1 --thinking off`

回答 agent 形态的独占问题：逐轮 TTFT 是否被 prefix cache 压平（history 滚大但每轮只 prefill 新增量）。
实测锚点：8 轮 ctx 5.1k→22.3k，TTFT 全程 0.95–1.3s 平坦 ⇒ 服务重启/缓存驱逐的成本要按此评估。

### 4. single·on 思考开销

`--turns single --concurrency 1 --thinking on`（放在便宜格子之后：贵，且对不稳的服务最危险）

回答：思考的成本结构——思考 token 占输出比例、思考耗时占 E2E 比例 ⇒ thinking 流量的容量规划系数；
`max_tokens_floor` 是否够（思考吃光预算 → 正文 0 字、finish=length，工具会告警）。
实测锚点：思考占输出 token 39%、占 E2E 时长 85–99% ⇒ 容量按输出预算 ×3–4 规划。

### 5.（条件）concurrent-multi·off 并发多轮

`--turns multi --concurrency 2,4`（CLI 自动置多轮，无需改配置）

**8 格矩阵里唯一值得补的组合格**：多 worker 各自滚 history 时的缓存共享与并发 prefill 形态，
场景 2/3 各只覆盖了一半。触发条件：业务形态是多用户 agent。便宜（无思考膨胀）。

## 2. 默认不测（及为什么）

| 格子 | 为什么不测 | 例外 |
|---|---|---|
| **单发多轮·on** | 思考开销已被 single·on 单独量化、多轮缓存已被 multiturn·off 量化，叠加即可预测。唯一增量是「思考内容进 history 后的缓存命中变化」这类二阶效应，撑不起 ~1h 串行窗口 | 无 |
| **并发多轮·on** | 三因素全组合：结果 = 并发曲线 × 思考膨胀 × 多轮平坦 TTFT 的叠加，且是**成本最高**（输出预算 ×3–4）、最容易把不稳服务打挂的格子 | 线上就是这个形态时改名「稳定性压测」：限时长 + 熔断开着 + 盯服务端日志，不按性能格子收集数据 |
| **部署不认的思考档位**（如部分部署没有 `high`） | 必 400 | 先用探针确认部署认哪些 `reasoning_effort` 再排格子 |

## 3. 条件触发才测

- **思考等级 low/medium/xhigh**（D 专项，换 `thinking.levels` 配置）：当 thinking 成本被判定为主要成本时——
  实测思考占 E2E 85–99%，这个条件基本总是成立。**性价比最高的一档，优先级高于任何组合格**
  （effort 档位是即时可用的成本杠杆，不用改部署）。注意 levels 模式下 `--thinking on/off` 失效，
  必须排在矩阵格之后跑，跑完换回配置。
- **并发·on（单轮或多轮）**：性能结果可预测，两种情况才跑——
  ① 排查 thinking 相关稳定性时作短跑探针（只跑一个档，兼任崩溃复现器）；
  ② 对外承诺的 goodput 覆盖 thinking 并发流量（goodput 衰减要实测而不是叠算）。
- **开环 Poisson（rate_sweep）**：只在容量规划/找饱和点时；闭环爬坡足够诊断瓶颈归属。
- **混合负载 mix**：当均匀负载的 goodput 与业务直觉明显不符时，验证长短混跑折扣与尾延迟。
- **trace 回放**：filler 结论要向真实流量外推时（token 分布、多轮深度与 filler 系统性不同的场景）。

## 4. 执行顺序与纪律

```
预检标定 → single·off → concurrent·off → multiturn·off → single·on → 思考等级 → 条件格
```

便宜、信息密度高的先跑；贵的思考格放后；并发×on 放最后（叠加崩溃风险，且随时可砍）。

- **盐值纪律**：每轮唯一 `--seed-salt`（prefix cache 是显存 LRU，换盐才保证冷路径成立）；盐值接续递增，废轮不复用。
- **每格独立输出目录**；失败/半程数据立即隔离，不进报告（服务中途死亡的轮次，未完成请求会统一带同一时间戳，一眼可辨）。
- **跨重启数据分段标记**：服务重启清空 prefix cache、可能改了参数，前后的轮次不可直接对比。
- **改了服务端参数必须同步部署文件**（compose/IaC），否则下次重建容器口径漂移。
- **稳定性事故 > 一切数据**：出现挂死/失联，先停队列、留现场（时段 + 当时正在跑的档位 + 客户端挂住的请求形状），再谈补测。

## 5. 反例清单（真机轮踩过的，别再踩）

1. **空闲窗口均值当稳态**：服务端日志 `Avg generation throughput: 16.6 tok/s` 是空闲窗口均值，
   实际单流 55–107 tok/s——差点据此把 `min_tps` 定在会误触发的档位。
2. **SSE chunk 数当 token 数**：MTP 一步吐 ~4.5 token，按 chunk 计速低估 4.5×；速率一律以 `usage` 为准。
3. **半程数据混进报告**：服务中途死亡产生的 JSON 里，失败请求集中在死亡时刻，必须隔离。
4. **组合格当信息源**：并发/多轮/思考的交互效应实测都很弱（TPOT 21→23ms @并发 1→8），全矩阵铺完 8 格
   的边际信息接近零——4.5 格已经回答了全部瓶颈问题。
5. **把挂死当慢**：引擎无响应挂起时客户端流不报错、stall_guard 也不触发（无 token 吐出不计入），
   只能靠逐请求 timeout 兜底——挂死现场要靠服务端日志确认，客户端数据只能给出「从哪条请求开始」。
